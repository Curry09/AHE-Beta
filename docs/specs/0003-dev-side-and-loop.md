# 0003 · Developer Side and Closed Loop

<!-- This file is maintained by the spec tool: the frontmatter is the structured source data (including the tasks DAG), and the body is a group-level overview in the nine-section rust-RFC format. -->

## Summary

This group implements **b｜developer side** and **c｜closed-loop feedback**, assembling the components from the first two groups into repeatable evolution rounds. One round = a (users produce issues + user experience) → b (developers modify the harness, test the user experience gate, and release) → c (the new harness version returns to a).

One closed-loop round (the responsible task is shown after each node):

```
a  user session (0001 run_session, harness=launch(release)) ─produces→ issue(Gitea) + user experience(SessionStore)
        │
b       ├ developer_agent(T3)  fetch issue → route by label → modify harness branch
        ├ test_agent(T4)       run N sessions on candidate ref, calculate average experience score, compare with release baseline → experience score gate
        └ release(T5)          if the gate passes, merge into release branch + create tag (= new version)
        │
c  orchestrator(T6) uses the new tag as the harness for the next round of a, repeating the loop; metrics(T6) records issue count over time
```

Supporting components: the **T1** launcher connects “a particular version of the harness program” to `HarnessInterface` from 0001 (the glue layer) and provides the v0 seed `harness_template`; **T2** is the nexau adapter layer shared by the user/developer/test roles. The core constraint of this group is: **the gate uses only user experience, and benchmark remains held-out throughout** (observed only afterward, with no role in release decisions).

## Motivation

Direct self-evolution from trajectories can easily bring trajectory characteristics into the harness and cause local overfitting to benchmark. The way forward is to separate the training signal (user experience) from the test signal (benchmark). This group implements that principle in two areas: “how developers iterate on the harness” and “how new versions return to the user side.”

The harness is an independently launchable program (with one or multiple agents), and the user side recognizes only HarnessInterface. Turning “the harness at a particular git ref” into an object that supports conversation requires a glue layer—this motivates the T1 harness launcher, which also provides the v0 seed harness_template as the starting point for evolution. In the MVP, the user/developer/test roles all use nexau as their sole runtime, differing only in their prompts and tool configurations. T2 therefore consolidates “loading definitions and running them” into a single nexau_runtime, avoiding a separate implementation for each role; the user_agent definition also fills in the part abstracted as “injecting an LLM” in spec-0001.

With these two supporting layers, issues must be able to become real changes to the harness: T3 developer_agent uses labels (bug/feature) to drive the branch strategy—bugs receive quick fixes on release, while features incubate on separate branches. This is where CLAUDE.md's use of a “branching model” to resolve the tension between “incremental patches vs structural changes” is put into practice. Releases, however, require an objective gate and must preserve train/test separation: T4 test_agent reuses the user-side run_session (“evaluating a harness” means “letting user agents run a few sessions with it to assess user experience”), using only user experience regression to decide whether to approve it, with benchmark held-out throughout. Once the gate passes, the closed loop needs a “finalization” action that turns the candidate into a stable version usable by the user side: T5 release merges the candidate into the release branch and creates a tag, providing a version identifier that can be pinned and traced back.

Finally, all the preceding components are individual parts that need assembly: T6 orchestrator defines how to run one a→b→c round and how many rounds to run; metrics in the same task implements the “issue count~time curve” required by CLAUDE.md to determine whether exploration (new issues) and convergence (resolution) are balanced.

## Guide-level explanation

The entire system is presented externally as a repeatable pipeline consisting of two supporting layers and three main stages. Supporting layers: T1 launcher connects “the harness being evolved” to HarnessInterface from spec-0001—it retrieves a harness version by git ref, starts its bundled entry, and adapts its black-box turn-by-turn protocol to send/reset/close; harness_template provides v0 (a single nexau) as the starting point. T2 nexau_runtime is a single nexau adapter layer that loads a role definition (prompt+tools) into a callable agent shared by the user/developer/test roles, and delivers the user_agent role definition as its first consumer to verify that the adapter runs.

On this foundation, the three steps of stage b occur in sequence: T3 developer_agent retrieves one open issue from Gitea, routes it to the appropriate branch strategy based on its label, and uses nexau to modify and commit the harness bundle (a single agent running sequentially in the MVP); this is the core of stage b in the closed loop. T4 test_agent runs a fixed set of N user sessions with the candidate harness ref, computes the average user experience score, and compares it with the current release baseline, approving it if there is no regression—this is the release gate, and it uses only user experience; benchmark does not participate in the decision. T5 release merges the candidate branch that passed the user experience gate into the harness repository's release branch and creates a tag; the tag is the version pinned by the user side in the next round, while rejection leaves release untouched.

T6 brings everything together at the outermost layer: orchestrator connects the user side (a), developer side (b), and feedback (c) into repeatable evolution rounds; metrics uses Gitea and local sessions to compute issue counts over time and user experience trends—providing assembly and observation for the entire system.

## Reference-level explanation

This group consists of two supporting layers and three main stages: T1 (launcher/harness_template) and T2 (nexau_runtime) form the foundation; T3 (developer_agent)→T4 (test_agent)→T5 (release) form the stage b pipeline; T6 (orchestrator/metrics) connects a→b→c into repeatable rounds at the outermost layer. See the end of this section for the complete dependency DAG.

**Supporting layer: launcher and harness_template (T1)**. The launch contract defines how the harness program interfaces with the launcher: params.yaml declares the launch command, containing at least `entry` (an argv list) and optional `cwd` and `env`. The launcher starts a subprocess accordingly, without hardcoding an interpreter or paths. After starting, the subprocess enters a turn-by-turn loop, reading one JSON `{"message": str}` per line from stdin and writing one JSON `{"reply": str}` per line to stdout (JSONL, with strict one-read/one-write pairing). How 1 or N nexau instances are orchestrated internally, and how many internal steps the harness takes in one turn, are invisible to the launcher. At the type level: `HarnessLauncher(harness_repo: str).launch(ref: str) -> HarnessInterface` (HarnessInterface is the send/reset/close protocol of spec-0001/T2); internally, `_checkout(ref)` uses git to retrieve a ref from the harness repository into `data/harness_runs/<ref>/` (reusing it if it already exists, ensuring idempotency for the same ref). Returned handle semantics: `send` writes one line, reads one line, and returns the reply string; `reset` terminates the current subprocess and restarts entry (the harness itself is not required to support a reset command); `close` terminates the subprocess and releases the pipes, and is idempotent. In sequence, launch first calls `_checkout` once and then starts the first subprocess; `reset` is equivalent to closing the old process and starting a new one; the handle cannot be used after close. Error handling: subprocess startup failure, a subprocess that has already exited at send time or EOF read from stdout, invalid JSON output or a missing `reply` key, and a nonexistent ref all explicitly raise errors instead of returning silently; close is idempotent. Key decisions: use a subprocess+stdio JSONL rather than import or HTTP, treating the harness as an external black-box program without depending on its language, dependencies, or internal structure, leaving room for CC/codex compatibility; the tradeoff is process and serialization overhead, which is acceptable at the scale of personal use. Implement reset by restarting the subprocess rather than through a protocol command, keeping reset semantics on the launcher side so that harness_template does not need to implement reset. Check out to `data/harness_runs/<ref>/` rather than a temporary directory to allow reuse of the same ref and manual inspection, consistent with the local data/ layout of SessionStore/metrics. Use complete per-turn JSONL messages as the transport unit rather than streaming chunks, matching HarnessInterface's send→complete reply semantics and keeping implementation minimal. harness_template is delivered with T1 as the v0 seed: entry.py (starts a single nexau), params.yaml (declares the launch command), and agents/main.md (a single-agent definition). Unit tests use a minimal fake entry (echo/scripted replies, without depending on real nexau) to verify consistent sending and receiving across multiple turns, cleared state after reset, idempotent close and errors on send after close, reuse of the directory when checking out the same ref, and three categories of failure paths: a nonexistent entry command, protocol violations (invalid JSON/missing reply), and premature exit (EOF). All T1 files: `backend/ahe_beta/harness/launcher.py`, `backend/harness_template/entry.py`, `backend/harness_template/params.yaml`, `backend/harness_template/agents/main.md`, `backend/tests/harness/test_launcher.py`.

**Supporting layer: nexau_runtime and role definitions (T2)**. Role definitions reside in `backend/agent_defs/<role>/`: prompt.md is required, and an optional tool configuration declares the tools available to the role; `load(agent_def_dir: str) -> Agent` reads the directory and parses the prompt and tool configuration to construct an Agent, raising an error if the directory or prompt.md is missing. `Agent.run(input: str) -> str` is a thin wrapper around the underlying nexau—it executes one call using the loaded role definition as system-side context and returns the output, without prompt engineering or retries and without retaining multi-turn memory; context assembly is the responsibility of the consumer (UserAgent in spec-0001). In sequence, load runs once (reading the definition and creating the client), and the consumer can call run repeatedly to drive multiple turns, but each call is independent. Error handling: if agent_def_dir does not exist or prompt.md is missing, load raises an error identifying the missing item; if a nexau backend call fails (network/authentication), run propagates the error without swallowing it at this layer. Without tool configuration, Agent is a text-only conversational role; user_agent takes this form. Key decisions: the three roles (user/developer/test) share the same load/run, differing only in prompts and tool configurations, consolidating “loading definitions and running them” in one place to avoid a separate adapter for each role. run remains a thin, stateless wrapper because multi-turn orchestration and context assembly are already owned by the consumer; nexau_runtime performs only the single transformation from “definition→callable object.” This task delivers `backend/agent_defs/user_agent/prompt.md` as the first consumer. Unit tests (mock nexau) cover load reading the definition and constructing an Agent, run forwarding inputs and returns (mock assertions), errors when the directory or prompt.md is missing, successful loading of the user_agent directory and one successful run call, and run propagating rather than swallowing errors from underlying calls. All T2 files: `backend/ahe_beta/nexau_runtime.py`, `backend/agent_defs/user_agent/prompt.md`, `backend/tests/test_nexau_runtime.py`.

**First step of stage b: developer_agent (T3)**. `work_one()` executes the following in order: ① Retrieve one open issue (including number/title/body/labels) through IssueTracker (spec-0002/T2 GiteaTracker at runtime); if there are no open issues, return an empty result without creating a branch. ② Determine the branch strategy by label—if the issue has the `bug` label, create the quick-fix branch `fix/issue-<n>` from release; if it has the `feature` label, create `feat/issue-<n>`; if neither is present or they conflict, treat it as a bug (the default strategy, with a comment noting that routing used the default). ③ Check out the harness repository into the working directory, then create and switch to a new branch based on release HEAD (the branch name includes the issue number for traceability). ④ nexau(developer_agent definition).run reads the issue + harness bundle contents and produces modifications to the bundle. ⑤ Commit (with a message referencing the issue number)/push to that branch, and use tracker.add_comment to leave a comment on the issue linking the branch name. Both types of branches start from release; they differ only in the merge timing in T5 (quick fixes for bugs, merging after incubation for features) and naming prefix, making them easy to distinguish manually and in orchestration. At the type level: `DeveloperAgent(tracker: IssueTracker, harness_repo: str, nexau_agent: Agent).work_one() -> DevResult` (DevResult: issue_number? / branch? / commit? / changed: bool). Error handling: if there are no open issues, return an empty DevResult without creating a branch or raising an error; if nexau produces no file changes, do not create an empty commit, and only leave an explanatory comment on the issue and mark it as having no commit; push or checkout failures raise errors with the issue number and branch name. Key decisions: label-driven branch routing puts into practice CLAUDE.md's use of a “branching model” to resolve the tension between “incremental patches vs structural changes.” Both types of branches start from release rather than a long-lived dev branch, maintaining a single baseline in the MVP, avoiding the complexity of merging multiple baselines, and centralizing merge strategy in T5. work_one handles only one issue and returns an empty result if there are no issues, moving the orchestration decisions of “how many to process/when to stop” up to T6 and giving the agent itself a single responsibility with repeatable invocation. Unit tests (mock nexau + FakeTracker/GiteaTracker + temporary git repository) cover creating an `fix/issue-<n>` branch and committing for a bug issue, creating an `feat/issue-<n>` branch and committing for a feature issue, returning an empty result without creating a branch when there are no open issues, creating no commit and leaving a “no changes” comment when nexau makes no changes, a comment linking the branch name appearing on the issue after processing, and taking the default (bug) path and noting it in the comment when the label is missing. All T3 files: `backend/ahe_beta/dev/developer_agent.py`, `backend/agent_defs/developer_agent/prompt.md`, `backend/tests/dev/test_developer_agent.py`.

**Stage b, step two: test_agent experience gate (T4)**. `evaluate(candidate_ref) -> Verdict` executes the following in order: ① `launcher.launch(candidate_ref)` obtains the candidate HarnessInterface; ② for a fixed set of (persona, scenario) pairs, run `run_session×N` for each scenario (|set|×N sessions in total), collecting FeelingScore.score for each session; ③ compute the candidate mean, mean_candidate; ④ obtain baseline, the historical mean experience score for the release version on the same fixed set (aggregated via the SessionStore index); ⑤ return pass if `mean_candidate >= baseline - tol`, otherwise fail. tol is the tolerance that absorbs experience noise; the criterion is “the candidate is not significantly below the baseline,” with equality passing (a tie passes). N is the number of sessions per scenario; averaging multiple sessions reduces per-session variance. N and the decision method (mean + tolerance vs. a distribution test, such as Welch t / a one-sided interval) are listed as open spec items; the MVP uses mean + tolerance. The held-out guarantee is established at the signature level: evaluate accepts only candidate_ref, the fixed persona/scenario set, and baseline experience scores, and accepts no benchmark data source; experience scores come only from run_session's FeelingScore, with no path connecting them to benchmark scoring. Benchmarks are observed only on the side through T6 metrics and do not enter Verdict. At the type level: `TestAgent(launcher: HarnessLauncher, fixed_set: list[tuple[Persona, SeedScenario]], baseline: float, n: int, tol: float).evaluate(candidate_ref: str) -> Verdict` (pass: bool / mean: float / baseline: float / n: int / per_session: list[int]). Error handling: when the baseline is missing (no release experience history in the first round), the MVP convention is to allow passage (pass), mark the baseline as unavailable in Verdict, and establish the first version as the baseline; an empty fixed set or N<=0 raises an error; a failed run_session (harness crash) is assigned the minimum experience score (1) rather than discarded, and the number of failed sessions is recorded, preventing crashed sessions from being silently ignored and inflating the mean; if the candidate fails to launch, evaluate raises an error. Key decisions: evaluation means “having the user agent run a few sessions with the candidate harness to assess the user experience,” reusing spec-0001 run_session so that evaluation and training signals share a source and the gate metric aligns with the optimization objective; averaging N sessions is the simplest way to reduce per-session variance; allowing ties (>= baseline - tol) makes the gate block only “regressions,” not “lack of improvement,” avoiding stalled exploration; assigning failed sessions 1 point rather than discarding them prevents “skip on crash” from making unstable candidates more likely to pass the gate. Unit tests (FakeHarness + mock LLM injecting experience scores, with no dependency on a real model or launcher) cover the three decisions for candidate mean > baseline, the == baseline - tol boundary, and < baseline - tol; configurable N (asserting that the number of run_session calls = |set|×N); passage with an unavailable-baseline marker when the baseline is missing; assigning 1 point when a session raises an error without interrupting the entire evaluation; and errors for an empty fixed set or N<=0. All T4 files: `backend/ahe_beta/dev/test_agent.py`, `backend/agent_defs/test_agent/prompt.md`, `backend/tests/dev/test_test_agent.py`.

**Stage b, step three: publishing a release (T5)**. `release(harness_repo, candidate_branch, verdict, tracker?, issue_number?) -> ReleaseResult`: when verdict.pass is true, merge candidate_branch into the release branch in the harness repository using a merge commit (preserving candidate history), create a new tag (version number = current maximum version + 1, starting at v1 if there are no tags), close the associated issue if tracker and issue_number are provided, and return `ReleaseResult(released=True, tag=<new tag>, ref=<new release HEAD or tag>)`; when verdict.pass is false, do not merge, create a tag, or modify the release branch; if tracker and issue_number are provided, comment on the issue with the rejection reason (taken from Verdict's mean/baseline), and return `ReleaseResult(released=False, tag=None)`. Version numbers are monotonically increasing integer counters; the new version number = the maximum value found by scanning existing tags in the harness repository +1. The tag is the version identifier that the user side pins in the next round (T6 uses ReleaseResult.ref/tag as the ref for the next round's launch). At the type level: `release(harness_repo: str, candidate_branch: str, verdict: Verdict, tracker: IssueTracker | None, issue_number: int | None) -> ReleaseResult` (ReleaseResult: released: bool / tag: str | None / ref: str | None). Error handling: a nonexistent candidate_branch raises an error; for merge conflicts, the MVP does not resolve conflicts automatically, raises an error, and leaves the release branch unchanged; when tracker/issue_number are omitted (None), skip issue status/comment operations and perform only the git merge + tag; repeated calls for the same already-merged candidate follow the rule “no new tag without an actual diff,” treating the merge as a no-op (idempotent) to avoid empty versions. Key decisions: releasing is a lightweight merge + tag operation without introducing a version management framework; its semantics are simply “establish a stable point that can be pinned”; version numbers use a monotonic counter rather than semantic versioning, since the MVP has no need for major/minor/patch semantics, and comparability, sortability, and traceability suffice; issue closure/comments go through the optional tracker, decoupling releases from issue tracking so that git operations do not strictly depend on Gitea availability; the default merge strategy is a merge commit, consistent with spec-0002/T3's “use real branches/merges,” with conflicts failing explicitly rather than being resolved automatically to avoid silently incorrect merges. Unit tests (temporary git repository + FakeTracker) cover merging the candidate into release and creating a new tag on pass; leaving release HEAD and the tag set unchanged on fail; the corresponding issue status changes and rejection comments on pass/fail; performing only git operations without errors when tracker=None; raising an error and leaving the release branch unchanged when candidate_branch does not exist or a merge conflict occurs; and starting the first release at v1 when no tags exist. All T5 files: `backend/ahe_beta/dev/release.py`, `backend/tests/dev/test_release.py`.

**Integration and observation: orchestrator and metrics (T6)**. `run_round(release_ref) -> new_release_ref` connects one round of a→b→c: a) for a fixed/sampled set of (persona, scenario) pairs, run run_session with `harness=launcher.launch(release_ref)`, sending generated issues to Gitea (via IssueTracker) and experience scores to SessionStore; b) `developer_agent.work_one()` takes one issue, modifies the harness, and produces a candidate branch → `test_agent.evaluate(candidate_ref)` produces Verdict → `release(harness_repo, candidate_branch, verdict, ...)` produces ReleaseResult; c) if released, `new_release_ref = ReleaseResult.ref/tag`; otherwise retain the old release_ref, with the return value becoming the input to stage a of the next round. `run(n_rounds)` starts from the initial release_ref, repeatedly calls run_round, feeds each return value into the next round, and records the release_ref chain across rounds. When stage a produces no issues, stage b has no open issue to process, or test_agent rejects the candidate, no release is published in that round and new_release_ref = release_ref, but the round still counts and metrics still record that round's stage-a output—the loop does not stop because one round fails to pass the gate. Metrics contract: `issue_curve()` retrieves issue created/closed timestamps from Gitea and produces a time-ordered (opened, closed, net_open) series, where net_open = cumulative opened − cumulative closed, corresponding to the “net unresolved issues” curve in CLAUDE.md; `feeling_trend()` retrieves per-session experience scores and timestamps from the SessionStore index and produces an experience-over-time series (with means optionally aggregated by round/time window); benchmark scores (if any) are displayed alongside these two only as an observational series and do not participate in any run_round decisions. At the type level: `Orchestrator(launcher, fixed_set, tracker, store, developer_agent, test_agent, release_fn)` uses dependency injection throughout, `run_round(release_ref: str) -> str`, `run(n_rounds: int) -> list[str]` (the release_ref chain across rounds); `Metrics(tracker: IssueTracker, store: SessionStore)` provides `issue_curve() -> list[tuple]`, `feeling_trend() -> list[tuple]`. Error handling: `n_rounds <= 0` raises an error; if a stage-b component (developer/test/release) raises an error in a round, that round fails and the error propagates; orchestration does not silently swallow errors, and run may record completed rounds before aborting; empty metrics data sources (before the first round) return empty series without raising errors. Key decisions: run_round takes and returns release_ref, making “version feedback” explicit in the function signature; stage c of the loop is simply “feed the return value into the next round's input,” with no hidden state; the MVP uses sequential rounds (complete all of a before b) rather than a pipeline/concurrency, keeping orchestration readable and unit-testable; rounds without a release retain the old ref, so the loop does not stop because a round fails the gate, allowing sustained execution across multiple rounds and aligning with “long-term observation of issue curves”; metrics only read Gitea + SessionStore, without creating their own storage or dual-writing alongside authoritative sources: Gitea is authoritative for issues and SessionStore for experience scores; resumable execution and checkpoints are outside this task's scope, and run_round/run remain pure orchestration (no hidden state, unit-testable); recovery from ephemeral sandboxes is handled by an outer wrapper in spec-0004's harbor runner—calling run_round round by round and save_checkpoint each round; run() itself does not perform checkpointing. Unit tests (with injected mock components) cover the run_round call order a→b→c (run_session first, then work_one→evaluate→release); returning a new ref when Verdict.pass is true and the old ref on rejection; chained feedback in run(n_rounds) (input to round k = return value of round k-1) and return length; no release when stages a/b have no issues while still counting the round; issue_curve producing the correct series for constructed created/closed timestamps; feeling_trend producing the correct series for a constructed SessionStore index and returning an empty series for empty data; errors for n_rounds<=0; and propagation of stage-b component errors without orchestration swallowing them. All T6 files: `backend/ahe_beta/loop/orchestrator.py`, `backend/ahe_beta/loop/metrics.py`, `backend/tests/loop/test_orchestrator.py`, `backend/tests/loop/test_metrics.py`.

## Rationale and alternatives

The tradeoffs in this group repeatedly return to three fundamental questions spanning components: how far black-box isolation should go, whether the cost of trusting only user experience for the gate is acceptable, and how “heavy” orchestration should be.

**Integration approach and runtime abstraction (T1/T2)**: among subprocess + stdio JSONL, Python import, and local HTTP, the launcher uses subprocess + JSONL—it makes no assumptions about the harness's internal implementation, maximizes decoupling, and aligns with the long-term goal of “CC/codex compatibility,” at the cost of process startup and serialization overhead that is acceptable at the scale of personal use; import requires the harness and this repository to share a language and dependencies, violating the black-box principle, while HTTP introduces port and service lifecycle management and is too heavy. Among restarting the subprocess, adding a reset command to the protocol, and launching anew for every session, reset uses subprocess restart—semantics stay concentrated on the launcher side, and harness_template does not need to implement a reset command; adding a protocol command would increase the contract burden on the harness side, while launching anew for every session would repeat checkout work and be wasteful. Checkout persists to `data/harness_runs/<ref>/` for reuse rather than using a temporary directory each time, enabling idempotent reuse of the same ref and manual inspection while aligning with the local data/ layout of SessionStore/metrics; the protocol transport unit is a complete JSONL payload per turn rather than streamed chunks, matching HarnessInterface's send→complete reply semantics and keeping implementation simplest, with streaming deferred until real interaction reveals a need. nexau_runtime chooses a thin wrapper around nexau alone over reserving an abstraction layer for multiple runtimes (YAGNI/Occam)—CC/codex integration is a later goal, and an extra abstraction layer now would only add complexity; dispatch can be added inside load when integration happens. Among a directory + prompt.md (+ optional tool configuration), a single YAML manifest, and in-code constants, role definitions use a directory layout—Markdown prompts are easy for people to write and read, tool configurations can be mounted optionally, and all three roles share the same structure; putting long prompts into fields in a single YAML file makes editing awkward, and in-code constants cannot be modified by non-engineers. run uses a stateless single invocation rather than a built-in multi-turn session object, because multi-turn semantics are already owned by UserAgent/run_session; keeping another copy of session state in the runtime would duplicate the consumer's state and make drift likely.

**Branch and version model (T3/T5)**: For developer_agent concurrency, choose a single serial agent (Occam's razor) rather than multiple concurrent agents: concurrency introduces branch conflict resolution and issue contention, which the MVP does not need; add it after scaling. For routing granularity, choose two labels, bug/feature, rather than multidimensional routing with priority/type: the two labels directly drive the two branch paths and are sufficient; add finer classifications later as needed. For the feature branch baseline, branch from release rather than a long-lived dev branch to maintain a single baseline and simple merge semantics; a long-lived dev branch introduces a second merge, which is unnecessary for the MVP. For handling no changes, choose a comment explaining the situation and no empty commit rather than forcing an empty placeholder commit, because empty commits pollute history and carry no information, while a comment already provides traceability. For the release version identifier, choose a monotonically increasing counter tag (Occam's razor) over semantic versioning (semver) or commit sha: it is sortable and can be pinned without major/minor semantics; semver requires change classification rules and is premature, while sha is unreadable and does not express version order. For merging, choose merge commit rather than fast-forward or squash to preserve candidate branch history and align with “use real branches/merges”; ff requires linear history, and squash loses history. For conflict handling, choose an explicit error (MVP) rather than automatic conflict resolution or forced overwrite, because automatic resolution is complex and error-prone, and forced overwrite would lose existing release changes; explicit failure leaves handling to the upper layer or a human. Make issue integration an optional tracker parameter rather than requiring a tracker, because release is fundamentally a git operation and issue tracking is a side path; decoupling facilitates testing and offline operation.

**Gate philosophy (T4)**: For the decision method, choose mean + tolerance (MVP) over distribution tests (t-test/interval) or single-session comparison: it is simplest and robust for small N; distribution tests are more rigorous but require a significance level and sample size to be established first, so they are listed as unresolved; single-session comparison has too much variance to be usable. For gate signals, choose experience only over a combination of experience and benchmark: this preserves train/test separation and held-out status, at the cost of potentially allowing changes that worsen benchmark performance, which the design explicitly accepts (benchmark is observation-only and does not vote). For failed sessions, assign the minimum score rather than discarding them or failing the entire evaluation: this neither silently ignores failures nor lets an occasional single-session crash veto the entire evaluation. When the baseline is missing, let the first version pass and set it as the baseline rather than blocking for a human-provided baseline, because the loop must bootstrap itself and the first version is naturally the baseline for subsequent versions; blocking would stall the first round.

**Orchestration granularity (T6)**: Choose a sequential single-round a→b→c orchestration (Occam's razor) rather than pipelining or concurrently running multiple sessions and issues: the logic is clear and easy to unit test; concurrency introduces session/branch scheduling and can be optimized after scaling. For feeding versions back, have run_round explicitly receive and return release_ref rather than having the orchestrator maintain internal current-version state, making segment c of the loop visible in the signature, avoiding hidden state, and facilitating per-round injection and replay. For rounds without a release, continue using the old ref rather than aborting the loop, because observation metrics require long-running operation to see whether the issue curve is balanced; failing the gate in one round should not terminate the entire evolution. For metrics storage, choose read-only access to Gitea+SessionStore rather than building a separate metrics database (Occam's razor): this avoids drift from dual writes to the authoritative sources; aggregation is computed on read, which is acceptable for the small data volume. Place benchmark in the metrics observation side path rather than in orchestration/the gate, preserving held-out status and train/test separation; benchmark only verifies and does not vote.

## Prior art

The precedents for all components are within this group or in earlier specs: T1 launcher builds on the HarnessInterface protocol (send/reset/close) from spec-0001/T2 and the harness repository/release branch source from spec-0002/T3, implementing the CLAUDE.md architecture “object being evolved: harness as a launchable program” and “compatible with claude code / codex integration”. T2 nexau_runtime corresponds to CLAUDE.md “nexau as the agent implementation, compatible with claude code / codex integration”; its first consumer is spec-0001/T3 UserAgent, and the multi-turn orchestration entry point is spec-0001/T4 run_session. T3 developer_agent depends on T2's Agent, the IssueTracker interface from spec-0001/T5 and the GiteaTracker implementation from spec-0002/T2, and the harness repository and release branch from spec-0002/T3, corresponding to CLAUDE.md method b “bug → release branch, large feature → feature branch”. T4 test_agent reuses spec-0001/T4 run_session and spec-0001/T6 SessionStore (baseline index), depends on T1 launcher, and implements the CLAUDE.md constraints “the release gate uses experience only; benchmark is used for observation only” and “benchmark remains held-out throughout”. T5 release consumes T4's Verdict and operates on the harness repository and release branch from spec-0002/T3 using IssueTracker.set_state/add_comment from spec-0001/T5 and spec-0002/T2, corresponding to CLAUDE.md method b “the test agent performs internal testing before merge and release” and “if the gate passes, merge into the release branch + create a tag”. T6 orchestrator and metrics assemble all the preceding components (run_session: spec-0001/T4; SessionStore: spec-0001/T6; IssueTracker: spec-0001/T5; launcher: T1; developer/test/release: T3/T4/T5); the recoverable harbor run entry point and checkpoint are left to spec-0004, corresponding to CLAUDE.md “c｜closed loop: the new harness after release returns to the user side, repeat”, “observation metrics: record the curve of issue counts over time”, and “benchmark remains held-out throughout”.
