# 0027 · Unified Agent Structured Output Contract: issue_schema as the Single Source of Truth + Native submit-tool Validation

<!-- This file is maintained by the spec tool: frontmatter is structured source data (including the tasks DAG), and the body is a nine-section group-level rust-RFC overview. -->

## Summary

Unify the three agents that produce structured output (user sim / triage / architect) from three approaches with different levels of strictness and patches piled on patches into one clean path: **issue_schema as the single source of truth for normalized fields → generate the submit tool's input_schema → the agent natively emits structured output using the schema-bearing submit tool → nexau enforces jsonschema validation at the tool-call layer (retrying on violations) → the driver directly reads validated parameters and uses one shared fallback/persistence path**. Remove triage's second LLM reformatting call, brace scanning on both sides, and per-agent alias normalization; acknowledge that the user body is free text (real users do not fill out templates), and remove the dead USER section of issue_schema. This is purely a refactoring of output paths: no changes to closed-loop semantics and no benchmark.

## Motivation

Review of the current implementation (evidence):

1. **The USER section of issue_schema is dead code**: the user sim produces free text via `report_issue(body)` (`user/sim/tools.py`), and `sim_user._issue_draft_from_body` puts the body directly into the issue and adds labels; `render/validate(section="user")` has **zero calls** in production code (it appears only in `test_issue_schema.py`). The user prompt has no corresponding field constraints either. Half of the schema was never wired up.
2. **Constraint mechanisms are fragmented across all three sides**: one triage round = **2 LLM calls** (the agent does the work + `_normalize_dispositions` reformats it using `response_format=json_schema`); on failure, it falls back to `_parse_dispositions` brace scanning + `_disposition_of`/`_issue_num`/`_accept_fields` alias normalization. Architect has only `_parse_proposals` brace scanning + `_rfc_fields_by_label` tolerance; the user side has nothing.
3. **The root of the inelegance**: there is no unified mechanism for agent structured output. The schema is intended to be the single source of truth, but each output path goes its own way, enforcement differs, and the USER/TRIAGE split rests on the false assumption that users will fill out a template. Constrained decoding amounts to using a second LLM call to fix the first: expensive and still susceptible to drift.

Key fact: **nexau enforces jsonschema validation of parameters at tool-call time** (`archs/tool/tool.py:738 jsonschema.validate(params, self.input_schema)`, throwing `ToolValidationError` on violations). This means having the agent natively emit structured output through a submit tool with an input_schema is an existing capability: validate on emission, retry on drift, and handle it in one call without post-hoc reformatting or parsing.

## Guide-level explanation

After unification:

- **issue_schema** describes only the fields of the normalized artifacts (by kind) and is the single source of truth for the contract. The body of an issue reported by a user remains free text (the persona writes like a real person); there is no longer any pretense of a USER template.
- **triage** has an `submit_triage` tool: its parameter is a dispositions array (one item per issue, with fields/enums locked down by the schema-generated input_schema). The agent calls it when it wants to finish; nexau validates the parameters, rejects field drift or priorities outside P0-P3 immediately, and the agent retries. The driver always reads a compliant structure.
- **architect** likewise has `submit_rfcs`.
- **driver** reads canonical `Field.key` dictionaries directly → checks allowed/required fields for the selected kind and string values → applies the existing needs_info/skip fallback → persists. Unknown keys and display-label aliases are rejected, never normalized.

For users: more reliable output (validated on emission), lower cost (triage drops from 2 LLM calls to 1), and easier comprehension (one contract, one persistence path).

## Reference-level explanation

### Canonical keys and display labels

Normalized triage fields use `root_cause`, `boundary`, `acceptance`, and `deliverable`, restricted by kind.
RFC fields use `problem`, `root_cause`, `related`, `direction`, and `acceptance`.
Display labels are presentation only:

| Key | Display label |
|---|---|
| `root_cause` | Root cause |
| `boundary` | Boundary |
| `acceptance` | Acceptance criteria |
| `deliverable` | Deliverable |
| `problem` | Problem |
| `related` | Related issues |
| `direction` | Direction |

No Chinese or display-label keys are accepted, and no label-to-key conversion runs during parsing.
Current PM/Architect submit payloads retain their role-specific artifact keys; this change affects normalized projections and the issue/RFC contract, not those payload shapes.

### Generation, parsing, and persistence

- **T1 · issue_schema + agent_contract**: `SCHEMAS` is the single source for normalized field keys, string types, required/optional rules, declaration order, and English display labels. `dispositions_input_schema()` / `rfc_input_schema()` generate `fields` properties from `Field.key`, never `Field.label`. Triage's union of tool properties is checked again against the selected kind before persistence. `apply_records(...)` retains the existing needs_info/skip fallback; `validate` rejects unknown/nonstring fields and `render` reads canonical keys under display headings.
- **T2 · triage**: submit_triage tool input_schema = `agent_contract.dispositions_input_schema()`, configured as a **stop tool**; binding `submit_triage(dispositions, agent_state=None)` **returns `{"dispositions": dispositions}`**; `_run_agent` returns the return value of `agent.run`, and `triage_once` uses `json.loads` on it to obtain `dispositions` (parse failure = no-op fallback); simplify `_apply` (read validated `issue`/`disposition`/`fields`/`of` directly, keeping `fields` keyed by `Field.key`; remove `_normalize_dispositions`/`_parse_dispositions`/`_disposition_of`/`_issue_num`/`_accept_fields` and `output_contract_schema`); **the driver checks each kind's allowed/required fields and rejects nonstring normalized values** (the tool union does not replace per-kind validation); remove hand-written JSON from the systemprompt and instruct it to call submit_triage instead; allow sufficient max_iterations + retain the fallback of no-op when submit is not called.
- **T3 · architect**: submit_rfcs tool input_schema = `agent_contract.rfc_input_schema()`, stop tool; binding returns `{"proposals": proposals}`; `propose_once` uses `json.loads` on the return value of `agent.run` to obtain `proposals` → persist RFC + supersede; remove the parsing use of `_parse_proposals`/`_unwrap_result`; remove hand-written fields from the systemprompt.
- **Generated tool contracts**: regenerate checked-in `.tool.yaml` input schemas from `agent_contract` after changing `SCHEMAS`; drift tests require `yaml["input_schema"] == agent_contract.X()`. Do not maintain a second field-key list in YAML or prompts. A display-label change may alter rendered headings but must leave tool properties and parser acceptance unchanged.

Persisted triage submissions bypass live tool validation, so replay checks the full current `dispositions_input_schema()` before any tracker mutation.
An incompatible receipt returns `saved-submit-contract-mismatch` and leaves the issue unchanged; it is never converted through aliases.
Fresh submissions missing required per-kind values retain the existing `needs_info` fallback.

**DAG**: T1 → T2, T1 → T3 (T2/T3 can run in parallel after T1). Each file belongs to a single task, with no overlap.

**Non-goal**: Do not change closed-loop a/d1/d2/b/c semantics or division of responsibilities; do not change dev claiming/budget/carryover; do not introduce a benchmark; do not implement sharded scheduling for triage/architect (that is a separate scalability track for a future spec).

## Drawbacks

- Depends on the actual behavior of nexau tool-layer jsonschema validation and ToolValidationError→retry: T2/T3 must confirm in live runs that validation failures feed errors back to the model for retry rather than aborting directly; if not, fall back to submit tool + T1 shared tolerant fallback (still cleaner than the current 2 calls).
- A relatively large refactor touching 4 output paths; control risk through 3 tasks with non-overlapping files + passing tests for each task + behavioral equivalence (the four disposition paths / RFC covers remain unchanged).
- Removing the USER section acknowledges the current state; if users are actually expected to fill out templates in the future, that requires a separate design (but it would conflict with an authentic user experience).

## Rationale and alternatives

- **Why native submit-tool instead of retaining constrained decoding**: nexau already enforces validation at the tool layer, so submit-tool yields a compliant structure in one call; constrained decoding uses a second LLM call to fix formatting, which is expensive and adds another point of possible drift. The former is strictly better, and the contract shares its source with the schema.
- **Why remove the USER section rather than wire it up**: a real persona writes a free-form report; forcing a template is unrealistic and offers no value in wiring it up. The normalized output of triage is the dev's Definition of Ready, and the schema focuses on that.
- **Alternative**: Unify only triage/architect parsing and retain constrained decoding. This treats the symptom rather than the cause: it still requires two calls and remains disconnected from the USER section.
- **Alternative**: Retain brace scanning as a unified fallback without introducing submit-tool. This is easier, but gives up validation on emission and still requires post-hoc recovery from drift.

## Prior art

- spec-0025 established issue_schema and the USER/TRIAGE split, and separated triage/architect; this spec consolidates its unwired half and unifies the output mechanism.
- spec-0024's god-view progressive drill-down demonstrated the approach of letting tools carry structure and retrieving it on demand; submit-tool applies the same approach to output.
- nexau tool input_schema + jsonschema validation (`archs/tool/tool.py`) provides the capability underlying this proposal.

## Unresolved questions

The three original unresolved questions have been **empirically settled** against nexau in the production environment (T2/T3 can follow these directly; the fallback is unnecessary):

1. **Tool-layer strict validation = present** (`jsonschema.validate` in `archs/tool/tool.py` `Tool.validate_params`). Tested:
   invalid enum, missing required field, invalid enum in a nested item, extra key in a nested item (additionalProperties) → **all rejected**. **⚠️ Key pitfall**:
   `schema_params` filters out undeclared **top-level** keys before validation → **extra top-level keys are not rejected** (silently discarded). Therefore, the payload must be placed
   in a **nested array** (`{dispositions:[item…]}`), with `additionalProperties:false + required + enum` set at the item level
   → drifted fields (such as triage_decision) are rejected at the item level. **The schema generated by this spec's agent_contract has exactly this
   shape** (T1 is ready).
2. **Validation failures are fed back for retry**: this version of nexau **has no ToolValidationError class**; validation failure throws `ValueError("Invalid
   parameters for tool …")`; executor catches tool exceptions → constructs `ToolResultBlock(is_error=True)` → fed back to the model
   → retry on the next turn. Retry limit = agent `max_iterations` (no dedicated counter). **Therefore: allow sufficient max_iterations + retain
   the minimal safety net of "agent did not call submit → no-op/fallback for this round"**. ⚠️ The driver must **not import/catch
   ToolValidationError** (it does not exist); retries are automatic within `agent.run`.
3. **submit parameters flow through the stop-tool return value**: `executor.py` stop tool triggers → stop_tool_result → return value of `agent.run()`
   (non-strings are JSON-serialized). **Interface**: submit tool binding **returns validated params(dict)** →
   becomes the return value of `agent.run` → driver uses `json.loads` on the return value to obtain `dispositions`/`proposals`. Native path, no side-channel.

Field-label normalization is retired: parsers use canonical English keys directly. `validate` remains for strict per-kind checks, and `render` remains for English display headings.
