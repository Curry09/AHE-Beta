# 0001 · Minimal User Agent Harness Usage Path

## Summary

This group implements the **a｜user-side** of the evolution loop: it lets a user agent role-play a real user, use the harness for multiple turns according to a persona and seed scenario, and produce two types of signals—an **experience score** (training signal) and **issue** (bug/feature request). This group builds only the "minimal path," using Fake backends throughout, without depending on a real Gitea or real harness, and can be tested independently; real backends are provided by 0002 (Gitea) and 0003 (harness).

Data-flow backbone (running through T1…T6, with every subsequent task attached to this line):

```
Persona / SeedScenario ─► UserAgent(T3) ⇄ HarnessInterface(T2) ─► Transcript
                                  │
                                  ├─► FeelingScore 1–4(+reason) ─► SessionStore(T6) saved locally
                                  └─► IssueDraft 0..n ─[IssueTracker(T5)]► Gitea ─► IssueRef
        run_session(T4) collects the above ─► Session (structure defined by T1)
```

Read the diagram as the task structure: **T1** defines all data structures (the foundation shared by the remaining tasks); **T2** defines the conversation contract with the harness; **T3** is where the training signal is generated (whether the role-play resembles a real person determines whether the signal is genuine); **T5** defines where issues go; **T6** defines experience-score persistence; **T4** orchestrates them into the sole entry point for "running a session," `run_session`. Downstream: the 0003 loop directly reuses `run_session`.

## Motivation

The training signal for the entire evolution loop comes from "simulated real usage": a user agent uses the harness for multiple turns according to a persona and seed scenario, producing an experience score and issues. To make this signal reproducible, statistically usable, and consumable by developers, the inputs and outputs of one usage session must first be fixed into stable structures (T1). This is the foundation shared by the remaining tasks; without it, neither driving nor orchestration can proceed.

CLAUDE.md requires the harness to be compatible with nexau / claude code / codex. The user side should therefore depend only on a stable conversation protocol rather than being bound to a specific backend (T2)—this is also the boundary that decouples the "object being evolved" from the "evaluation scaffolding." Otherwise, every change of agent implementation would require changes to user-side code.

On top of the protocol, what truly determines whether the training signal is trustworthy is the driver itself (T3): whether the signal is "genuine" depends on whether the driver behaves "like a real person"—asking follow-up questions, taking detours, getting stuck, and giving up after becoming frustrated—instead of mechanically running a fixed number of turns.

Once the data structures, protocol, and driver are ready, loop orchestration (loop/) and statistics (metrics/) both need a stable "run one session" entry point. Assembly logic is kept in a single runner; upper layers only provide inputs and receive a Session, without needing to know how the conversation works internally (T4).

The two types of signals produced by a session have different destinations: issues are ultimately submitted to Gitea, but user-side logic and unit tests should not depend on a running service. The IssueTracker interface therefore isolates the backend—tests use FakeTracker, runtime injects GiteaTracker, and both are equivalent for run_session (T5). The experience score is itself a training signal and must be traceable and statistically usable. The complete Session is retained as evidence, while an index is provided for loop/metrics to plot issue/experience curves and for the dev side to retrieve regression baselines (T6).

## Guide-level explanation

The shared user-side data structures are defined uniformly by T1 and used by the remaining tasks: given Persona (user profile) and SeedScenario (seed scenario) as inputs, multiple conversation turns produce one Session, which contains a Transcript (conversation record), FeelingScore (a 1–4 experience score and its reason), IssueDraft (the user agent's draft issue title/body/labels), and IssueRef (the number/url/state receipt after the issue is submitted to Gitea). This task defines only the structures themselves and requires pure data with bidirectional serialization; conversation and scoring logic are implemented by later tasks.

The harness being used is abstracted by T2 into a unified multi-turn conversation protocol, HarnessInterface, decoupling the user side from specific agent implementations. This protocol is the stable boundary between the "object being evolved" (the harness) and the "evaluation scaffolding" (the user side): the user side depends only on the protocol; the concrete backend is a "launchable program" (internally it may contain one or multiple nexau processes orchestrated by its entry script) and is connected through a launcher (see spec-0003). T2 defines only the protocol and provides the FakeHarness test backend.

On top of the protocol, the T3 user agent driver simulates a real user: according to Persona and SeedScenario, it drives a multi-turn conversation with the harness, autonomously determines when the conversation should end, and produces an experience score (FeelingScore, 1–4 with a reason) when the session ends. This is where the training signal is generated. The signal's authenticity depends on how faithfully the driver reproduces real usage behavior (follow-up questions, detours, stalls, and giving up), rather than on mechanically running a fixed number of turns. Issue generation is implemented only as a minimal stub in this task; the concrete mechanism remains open (see Unresolved questions).

T4 provides the minimal usable user-side entry point: the single stateless function run_session orchestrates Persona, SeedScenario, HarnessInterface, and UserAgent into one session, collects Transcript, FeelingScore, and IssueDraft, and returns a structured Session. All dependencies are injected through parameters. The runner itself constructs no backend, making test substitution and reuse by upper layers (loop orchestration and metrics statistics) straightforward.

The two types of signals produced by a session flow into their respective outlets here: T5 abstracts the issue submission destination as the IssueTracker interface, so the user side is not bound to a specific tracker backend. This task provides an in-memory FakeTracker implementation, allowing run_session to be tested end to end without a Gitea environment; the real GiteaTracker implementation belongs to spec-0002. T6 persists the experience score and Session locally through SessionStore—complete files plus one overall index. The index carries the minimum information needed for experience curves and regression baselines (session_id, experience score, and time), so statistics can be computed without opening every complete file.

## Reference-level explanation

All data structures are implemented as dataclasses: pure data with no behavior, supporting bidirectional dict/json serialization. Protocols uniformly use typing.Protocol (PEP 544, structural subtyping); test and runtime backends are equivalent under the protocol and can replace one another without affecting upper layers. Experience scores and Sessions are stored locally at `data/sessions/`; issues are not stored locally, but are submitted from IssueDraft through IssueTracker to Gitea, with the receipt represented by IssueRef. The data flow within this group's scope is:

```
Persona ──────┐
              ├─► UserAgent ⇄ HarnessInterface ─► Transcript
SeedScenario ─┘       │
                      ├─► FeelingScore (1-4 + reason)
                      └─► IssueDraft (0..n) ─[IssueTracker]→ Gitea ─► IssueRef
          run_session collects ─► Session (contains transcript/feeling/issue_refs)
```

**Data model (T1)** defines seven dataclasses, layered according to their roles in a session: the given inputs Persona (identity, skill level, domain, goals, and speaking style; the source belongs to a later distill spec) and SeedScenario (initial request/task description, not a test case); the process product Transcript (an ordered list of (role, content) turns, with role ∈ {user, harness}); the session outputs FeelingScore (score:int(1..4) + reason:str, one per session, produced at the end of the session), IssueDraft (title/body/labels, 0..n per session), and IssueRef (number/url/state, the Gitea receipt); and the top-level Session (session_id/created_at/persona/scenario/transcript/feeling/issue_refs). Serialization contract: to_dict produces a purely JSON-serializable structure (nested dataclasses are recursively converted to dict, and datetime is converted to an ISO-8601 string); from_dict is its inverse and ignores unknown keys to support forward field evolution (old code does not break when reading new data). JSON rather than YAML is used for persistence because Sessions are appended one by one, and JSON lines support streaming statistics for experience curves/regression baselines; human readability is delegated to the summary/OVERVIEW views. Invariants are asserted at `__post_init__` (FeelingScore.score ∈ 1..4; every Transcript turn has role ∈ {user, harness}); out-of-range values fail during construction, with no external validator introduced. At the persistence boundary, experience scores and Sessions are stored locally (persisted by T6), while issues are not stored locally—the authoritative store is Gitea, and the local side keeps only the IssueRef receipt, preventing dual-write drift. `models.py` exposes the dataclasses above and their to_dict/from_dict methods, depends on no other module, and sits at the bottom of the dependency graph. Unit tests cover field-level equality for each dataclass round trip (to_dict/from_dict), including nested Session→Transcript/FeelingScore/IssueRef; construction-time assertion failures for out-of-range FeelingScore values (0/5) and invalid Transcript roles; empty-list defaults for IssueDraft.labels and Session.issue_refs; datetime serialization to and reversibility from ISO-8601 strings; and ignoring unknown keys in from_dict without raising an error.

**Harness conversation interface (T2)** abstracts the harness being used as the unified multi-turn conversation protocol HarnessInterface, the stable boundary between the "object being evolved" (the harness) and the "evaluation scaffolding" (the user side): the concrete backend is a "launchable program" (internally it may contain one or multiple nexau processes orchestrated by its entry script) and is connected through a launcher (see spec-0003); the user side depends only on the protocol itself. The protocol methods contain only a three-method set (new decision, Occam): `send(message: str) -> str` sends one user message and returns the complete reply for that turn (non-streaming, full text; the caller guarantees that message is non-empty; the return value must be str, and an empty string is valid and does not indicate an error); `reset() -> None` discards the current session state and returns to the starting point of a new session, idempotently; and `close() -> None` releases backend resources (processes/connections/handles), idempotently. The valid lifecycle is `(reset? · send* · close)`: reset is an explicit session-start action called by the orchestrator (T4) at the beginning of each session, and is not triggered automatically within the protocol, keeping the protocol free of implicit state; behavior after calling send/reset following close is undefined, and backends may raise an exception. FakeHarness chooses to raise RuntimeError to expose misuse. The call order of send corresponds one-to-one with the user turns in Transcript, and the harness replies correspond to harness turns; the protocol itself does not hold a Transcript, and transcription belongs to T3. The protocol does not specify retries or timeouts; exception propagation is passed upward, and the orchestration layer (T4) decides the handling strategy. The harbor episode/rollout batch interface is not reused directly because its input/output granularity is an episode rather than a single turn, creating a semantic mismatch with "turn-by-turn real-person conversation + user-determined termination" and requiring substantial adaptation. Extensions such as streaming output, tool-call receipts, and token/usage statistics are likewise excluded from the protocol methods for now under Occam, to be expanded if real nexau integration exposes a need. FakeHarness supports two injection modes (script: an ordered list[str], popped one by one in send order; or callback: Callable[[str], str], dynamically generating a reply from the input); the two are mutually exclusive and one is selected at construction. Internally it records `sent: list[str]` (all received messages) for unit-test assertions about send/receive order and count; reset clears sent and the script cursor; close sets the "closed" flag, after which send/reset raise RuntimeError. The script-exhaustion policy is to raise IndexError rather than silently looping or returning an empty string—the latter two would conceal a runaway T3 termination path (max_turns should truncate it rather than the script serving as a fallback), while raising an error directly exposes insufficient turn-count configuration in the test case. Interface: `HarnessInterface(Protocol)` { send / reset / close }; `FakeHarness(script: list[str] | None, callback: Callable[[str], str] | None)`: script and callback are mutually exclusive, and when both are absent the reply falls back to a fixed placeholder string; it exposes the read-only property `sent: list[str]` for assertions. Unit tests cover ordered responses for script injection, with sent matching the input sequence; dynamic responses for callback injection; construction-time errors for mutual-exclusion violations; clearing sent and resetting the script cursor after reset; RuntimeError from send/reset after close and no error from repeated close; IndexError on script exhaustion; and empty replies not being treated as errors.

**User agent driver (T3)** is where the training signal is generated. UserAgent is driven by an injected LLM backend (this group does not implement a specific model client): the LLM backend is specified as a Callable that takes organized context (a summary of persona/scenario/transcript) and returns text. UserAgent is responsible for organizing Persona/SeedScenario/Transcript into prompts and consuming the same backend through three parsers—message-generation parsing (extracting user_msg + end_flag), experience parsing (extracting score:int + reason:str), and issue parsing (extracting list[IssueDraft]). The main loop for one session (pseudocode):

```
reset is the responsibility of the orchestration layer (T4); UserAgent only consumes a ready harness
turn = 0
loop:
  user_msg, end_flag = parse(llm(persona, scenario, transcript))   # Generate this turn's user message and whether to end
  if end_flag → break                                            # Self-assessed: achieved / abandoned / had enough
  reply = harness.send(user_msg)
  transcript.append(user turn); transcript.append(harness turn)
  turn += 1
  if turn >= max_turns → break                                   # Fallback to prevent non-convergence
after the loop:
  feeling = parse_feeling(llm(...))        # 1..4 + reason, once at the end of the session
  drafts  = parse_drafts(llm(...))         # 0..n IssueDrafts (minimal stub, option a)
return (transcript, feeling, drafts)
```

Whether the signal is "genuine" depends on how faithfully the driver reproduces real usage behavior (follow-up questions, detours, stalls, and giving up), rather than on mechanically running a fixed number of turns. This is why self-determined termination with a max_turns fallback is chosen instead of a fixed turn count: a fixed count cannot express the real behavior of "stop when the goal is achieved/give up after becoming frustrated," which distorts the training signal; self-determination alone risks non-convergence, so max_turns closes the loop (counting user turns; when the limit is reached, the session ends forcibly even if the LLM has not sent an end signal, guaranteeing termination). The termination signal is encoded as an agreed textual sentinel (such as a fixed marker on the final line) rather than requiring JSON/tool-call schemas (new decision, Occam), avoiding excessive assumptions about model-backend forms and remaining compatible with the goal of supporting multiple agents/models; parsing failure is treated as "not ended," with max_turns providing the fallback termination. Experience and issues are both produced once after the loop ends (adopting the decision not to produce them every turn): the signals are cleaner, implementation is simpler, and this aligns with FeelingScore's "one total score per session" form; the cost is losing the fine-grained information about "which turn the experience began to worsen," which can be upgraded to per-turn output later if needed. Issue generation in this task implements only the minimal stub of option a (produced in character at the end of the session; the mechanism is not locked in, see Unresolved questions). For boundary handling, max_turns <= 0 fails an assertion at construction time (meaningless configuration); out-of-range experience parsing relies on the construction-time assertion in FeelingScore (T1), and UserAgent does not duplicate the check, preserving a single validation point; parsing zero issues is valid (most sessions have no issues); exceptions from harness.send are not swallowed at this layer and propagate upward for T4 to decide, consistent with the T2 protocol.

Interface: `UserAgent(llm: Callable[..., str], persona: Persona, max_turns: int)`, `run(scenario: SeedScenario, harness: HarnessInterface) -> tuple[Transcript, FeelingScore, list[IssueDraft]]`; max_turns > 0 is guaranteed by a construction-time assertion, and run does not call harness.reset/close (lifecycle belongs to orchestration layer T4). Unit tests (using a mock LLM that returns a fixed script) cover: exact session turn counts after an end signal is sent at a specified turn, with corresponding Transcript turns; truncating user turns to max_turns when termination never occurs; experience parsing producing a score in 1..4 with a reason; the sequence of messages received by FakeHarness matching the user-turn contents of Transcript one by one; correct behavior for issue stubs with zero and two issues; construction-time failures for max_turns<=0 and out-of-range experience (such as parsing 5); treating a missing end signal as not ended and terminating via max_turns; and allowing exceptions from harness.send to propagate without being swallowed by run.

**Session orchestration runner (T4)** provides a stable “run one session” entry point needed by both closed-loop orchestration (loop/) and statistics (metrics/): a single stateless function with all dependencies injected:

```
run_session(persona, scenario, harness, user_agent, tracker, store) -> Session:
    harness.reset()                                          # Start the session (lifecycle owned by the orchestration layer)
    try:
        transcript, feeling, drafts = user_agent.run(scenario, harness)
    finally:
        harness.close()                                      # Release backend resources regardless of success or failure
    issue_refs = [tracker.create_issue(d) for d in drafts]   # Submit each draft to the tracker
    session = Session(persona, scenario, transcript, feeling, issue_refs)
    store.save(session)                                      # Save the user experience and session locally
    return session
```

reset is called before user_agent.run, following the T2 agreement that “session initialization is the orchestration layer's responsibility”; UserAgent itself does not reset/close. close is placed in finally (new decision, Occam's razor): harness resources are guaranteed to be released even when UserAgent.run raises an exception, preventing backend handle leaks while allowing the exception itself to propagate upward. Submission and persistence occur only after run returns successfully—if run raises an exception, no IssueRef is produced and nothing is persisted, maintaining the rule that “failed sessions leave no partial artifacts”; issue_refs correspond one-to-one with drafts in order and are an empty list when there are 0 drafts. For error handling, this layer does not swallow exceptions from tracker.create_issue or store.save; they propagate directly upward (orchestration/retry policies belong to the loop layer). run_session performs no retries or idempotent deduplication; repeated calls for the same session produce duplicate submissions, and the caller is responsible for avoiding repeated calls. Dependency injection: harness satisfies HarnessInterface (T2), user_agent is a UserAgent (T3), tracker satisfies IssueTracker (T5), and store is a SessionStore (T6); tests replace all of them with FakeHarness + mock LLM + FakeTracker + a temporary-directory SessionStore, while runtime injects a real launcher/Gitea/local disk. Interface: `run_session(persona: Persona, scenario: SeedScenario, harness: HarnessInterface, user_agent: UserAgent, tracker: IssueTracker, store: SessionStore) -> Session`, a pure function with no global state beyond the returned copy; this function owns the harness lifecycle (reset/close), with close guaranteed to execute in finally. Integration tests (FakeHarness + mock LLM + FakeTracker + temporary-directory store) cover: normal completion returns a complete Session containing transcript/feeling/issue_refs; harness.reset/close are each called once, in the order reset → run → close; 2 drafts yield 2 numbered IssueRefs in corresponding order, and 0 drafts yield an empty issue_refs list; store.load restores an equivalent Session after run_session; in an early-abandonment scenario, the number of user turns is < max_turns but the Session is still complete; when mock UserAgent.run raises an exception, harness.close is still called, the exception propagates upward, store writes nothing to disk, and tracker receives no submissions.

**IssueTracker interface and FakeTracker (T5)** abstract the destination for issue submissions into an interface so that the user side is not tied to a specific tracker backend: `ensure_labels(names: list[str]) -> None` ensures that all specified labels exist and is idempotent (the Gitea backend first creates labels and resolves their IDs here; FakeTracker only maintains a set of names); `create_issue(draft: IssueDraft) -> IssueRef` creates an issue from draft.title/body/labels and returns a numbered receipt IssueRef(number, url, state), with a newly created issue initially in state "open"; `add_comment(number: int, body: str) -> None` appends a comment to the specified issue and raises KeyError if number does not exist (corresponding to 404 in the Gitea backend); `set_state(number: int, state: str, reason: str) -> None` changes the state, where state ∈ {"open", "closed"}, and reason records the reason for the change (aligned with Gitea state_reason semantics), raising KeyError if number does not exist. The backend allocates monotonically increasing numbers starting at 1, with an independent counter per instance (FakeTracker semantics align with Gitea's per-instance auto-increment); the backend constructs IssueRef.url from its number (FakeTracker combines a placeholder prefix + number into a deterministic url); create_issue does not deduplicate—submitting the same draft multiple times yields different numbers, consistent with Gitea behavior, and deduplication is the caller's responsibility. The protocol includes only four operations (create/comment/change state/create labels) rather than copying the full Gitea API (Occam's razor): this is the minimum sufficient set for the issue closed loop; milestones/assignment/search and similar features have no current consumers and will be added when the dev side needs them. “Not found” uses standard KeyError rather than a custom exception type, as there is currently no need to distinguish error categories. FakeTracker uses in-memory structures: `_counter: int` (number allocation cursor), `_issues: dict[int, dict]` (number → {title, body, labels, state, reason, comments}), and `_labels: set[str]`; create_issue increments _counter, writes to _issues, and returns IssueRef, aligning with Gitea semantics but without networking/persistence. It also exposes a read-only query for retrieving snapshots by number so unit tests can assert that comment/state changes took effect; the real GiteaTracker implementation belongs to spec-0002. Interface: `IssueTracker(Protocol)` { ensure_labels / create_issue / add_comment / set_state }; `FakeTracker()`: an in-memory implementation with monotonically increasing numbers starting at 1, exposing a read-only query for retrieving issue snapshots by number for assertions. Unit tests cover: two consecutive create_issue calls allocate numbers 1 and 2 with correct fields (number/url/state="open"); after add_comment, the snapshot read by number contains that body; set_state to closed+reason updates the state, and another set_state to open restores it; ensure_labels is idempotent (labels with the same name are not created twice), and an empty list is a no-op; calling add_comment/set_state with a nonexistent number raises KeyError, and passing an invalid state to set_state raises ValueError; two create_issue calls with the same draft yield different numbers (no deduplication).

**Local SessionStore (T6)** provides `SessionStore(root: str | Path)`: `save(session: Session) -> None` writes `root/<session_id>.json` (fully serialized through Session.to_dict) and appends one `{session_id, score, created_at, n_issues}` to `root/index.json`, automatically creating root if it does not exist; `load(session_id: str) -> Session` reads it back and restores all data through Session.from_dict, raising FileNotFoundError if the file does not exist; `index() -> list[dict]` reads all entries in root/index.json and returns an empty list if the index does not exist. Index entries are derived projections of the full files—score comes from session.feeling.score, created_at from session.created_at (an ISO-8601 string), and n_issues from len(session.issue_refs)—the full files are the sole source of truth, and the index can be rebuilt from them. The write order is “write the full file first, then append to the index” (new decision, Occam's razor): if the operation fails midway, at worst there is “a full file whose entry is missing from the index” (the index can be rebuilt from the full files), rather than the unrecoverable state of “an index entry without evidence.” Index appends use a single-file “read-modify-write” operation (load the existing index → append the new entry → write the whole index back), which is sufficient for the single-process MVP. Repeated save calls with the same session_id overwrite the full file but append duplicate entries to the index (new decision: save does not deduplicate index entries; deduplication is the responsibility of the caller/metrics consumer, keeping save simple and consistent with T4's “do not call repeatedly” agreement). Loading a nonexistent id raises FileNotFoundError (a standard exception, not a custom one); index() returns an empty list rather than raising an error when the index file is missing, since having no index on the first run is a valid initial state. Interface: `SessionStore(root: str | Path)` { save / load / index }; save automatically creates root if it does not exist, load raises FileNotFoundError for a nonexistent id, and index returns an empty list when missing. Unit tests cover: after save, both the full file and index contain the session, with correct index entry fields (session_id/score/created_at/n_issues); load restores an equivalent Session (field-level equality, including transcript/feeling/issue_refs); when root does not exist, save automatically creates the directory and writes successfully; index() returns an empty list when no index file exists and returns multiple entries in write order after multiple sessions are saved; n_issues matches the length of issue_refs (n_issues=0 when there are 0 issues); load raises FileNotFoundError for a nonexistent id; saving the same session twice overwrites the full file and leaves two index entries.

## Rationale and alternatives

For data modeling (T1), dataclass is chosen over pydantic/attrs (Occam's razor, zero dependencies). The lack of strict runtime validation is covered by `__post_init__` assertions + unit tests; pydantic can be reconsidered if schema export is needed in the future. json is chosen over yaml for persistence because it supports appending individual entries and is statistics-friendly, at the cost of readability, which is delegated to generated views. Session uses nesting rather than flat structures + foreign keys so that each session is self-contained and replayable from a single file, at the cost of requiring traversal for cross-session aggregation, which is acceptable at a small scale. Issues store only the IssueRef receipt rather than a full local copy, using Gitea as the single source of truth to avoid inconsistencies from writing to both local and remote storage.

For protocol design, both T2 and T5 choose typing.Protocol (structural subtyping) over ABC abstract base classes: Fake implementations and real backends satisfy the contract without explicit inheritance, reducing coupling and simplifying test doubles. Both deliberately narrow their method sets (Occam's razor): T2 retains only send/reset/close, without adding streaming/tool calls/usage statistics in advance—these requirements can only take shape after real nexau integration, and premature abstraction would lock in the wrong contract. It also does not directly reuse harbor's episode/rollout batch interface, because its input/output granularity is an episode rather than a single turn; adapting it to “turn-by-turn human conversation + user-determined termination” would require extensive adaptation and introduce a semantic mismatch. T5 includes only create/comment/change state/create labels rather than copying the full Gitea API; this is the minimum sufficient set for the issue closed loop, while milestones/assignment/search and similar features have no current consumers and will be added when the dev side needs them. “Not found” uses standard KeyError rather than a custom TrackerNotFound exception; there is currently no need to distinguish error categories, so a standard exception is sufficient, and an exception hierarchy can be introduced if unified error codes are needed later. FakeTracker uses independent per-instance numbering rather than global numbering, matching Gitea's “count per repository instance” semantics while keeping unit test numbering isolated and independently assertable. create_issue does not deduplicate, consistent with Gitea; deduplication is the caller's responsibility, avoiding implicit idempotency assumptions at the interface layer. send returns str rather than a structure containing metadata/usage because the user side currently needs only response text to write to Transcript, and additional metadata has no consumers (YAGNI). reset is explicit rather than implicitly resetting on the first send call, avoiding dispersing “session initialization” semantics into send, violating single responsibility, and making “session continuation” impossible to express. When the FakeHarness script is exhausted, it raises IndexError rather than silently looping or returning an empty string, exposing insufficient turn counts in test cases rather than hiding runaway T3 termination logic (which should be cut off by max_turns rather than a script fallback).

For driver behavior (T3), experience scores and issues are produced once at the end of the session rather than on every turn (adopted decision): this yields cleaner signals and a simpler implementation and aligns with FeelingScore's “one overall score per session” form, at the cost of losing the fine-grained detail of “which turn things started getting worse on”; if needed later, a new spec can upgrade this to per-turn output. Termination uses self-determination + a max_turns fallback rather than a fixed turn count: a fixed count cannot express realistic behavior such as “stop once the goal is achieved/give up after having enough” and would distort training signals, while self-determination alone risks non-convergence, so an upper bound provides a cutoff. Termination signals use an agreed sentinel/field rather than mandatory JSON/tool-call schemas (Occam's razor), because the latter make strong assumptions about model backend forms, conflicting with “compatibility with multiple agents/models”; parsing failures safely fall back to “not finished.” Three approaches were evaluated for issue generation—option a (in-character output at session end), option b (an independent analyzer reads the transcript and synthesizes findings), and option c (two steps: mark friction points + synthesize)—this group chooses a minimal stub for a without locking it in: a requires the least implementation effort and is sufficient to connect the full pipeline, while b/c are more accurate but introduce extra components; the choice can be revisited when the dev-side spec defines integration requirements. The LLM backend injects a generic Callable rather than binding to a specific client class, allowing unit tests to use fixed mock scripts and runtime to substitute real models, consistent with dependency inversion.

For orchestration responsibilities (T4), choose pure functions + dependency injection rather than a SessionRunner class holding dependencies (Occam's razor): this group has no state shared across sessions, so a class would only introduce an unnecessary lifecycle. When concurrency/batch requirements arise, wrap this at the loop/ layer without complicating this entry point. The harness lifecycle belongs to run_session rather than UserAgent: reset/close are orchestration concerns; placing them in UserAgent would give it both “conversation” and “resource management” responsibilities, violating the single-responsibility principle and hindering T3 unit tests (which would have to mock the lifecycle). Put close in finally rather than at the end of the normal flow: the latter would leak backend resources if run raises an exception, while finally guarantees release without masking the exception. For whether to persist failed sessions, choose to persist successful sessions only: persisting incomplete Session objects (missing feeling/transcript) would contaminate experience score curves and regression baselines. Prefer losing failed-session records, with the loop layer recording them separately as needed. The question of rolling back an already persisted session on submission failure does not arise: in this group, submission precedes persistence, and failures propagate immediately, so persistence never occurs and no rollback logic is needed (the ordering inherently avoids the problem).

For storage (T6), choose one file per session + a single aggregate index rather than a database (sqlite, etc.), because the scale is small and reads and writes are infrequent. Files require zero dependencies, and the complete records themselves serve as evidence; migrate when scale grows or complex queries become necessary. For the index, choose full “read-modify-write” of a single index.json rather than append-only JSONL, so index() can read it back as list[dict] in one operation. The cost is rewriting the entire file on each save, which is acceptable at this scale; switch to JSONL appends if session counts grow enough to make rewriting significantly costly. The index is derived from the complete records, and the complete records are authoritative rather than the index: the index can be rebuilt from the complete records, avoiding drift between two sources of authority. This also determines the order: “write the complete record first, then append to the index.” For index deduplication during save, choose no deduplication (Occam's razor): deduplication requires scanning the index first, increasing the cost of each save; duplicate saves are avoided through T4's “do not call repeatedly” convention, and deduplication belongs to consumers. Concurrency safety (file locking) is out of scope for this task; a single-process MVP is sufficient. Concurrency will be handled centrally when the loop layer orchestrates parallel execution, avoiding premature locking complexity in the storage layer.

## Prior art

The user side (a) of CLAUDE.md's “Method: simulated user usage → developer iteration” is the direct basis for this group: the mechanisms for producing the two signal types, experience scores + issues (T1 data structures, T3 driver), both follow from it. The specific form of the overall end-of-session score is clarified by this spec's requirements. Architecturally, this corresponds to “object being evolved: harness as a launchable program” and “compatibility with nexau / claude code / codex” (T2; the real backend launcher belongs to spec-0003), as well as “state destination: issue → Gitea” (T5; the GiteaTracker implementation belongs to spec-0002, and the IssueDraft/IssueRef structures belong to T1), “state destination: experience scores + session → local,” and the observation metric “issue count over time” (T6; downstream loop/metrics consume the index, and the Session serialization contract belongs to T1). Protocol design follows typing.Protocol (PEP 544, structural subtyping), on which both T2/T5 are based. T4's run_session is the implementation entry point for CLAUDE.md's user side (a), and the sole entry point reused by downstream loop/ orchestration of a→b→c, metrics/ calculation of issue curves, and the spec-0003 closed loop.

## Unresolved questions

The IssueDraft fields have been aligned with Gitea's issue-creation parameters (title/body/labels), and T1 adopts this triple. However, its production mechanism (who generates it and when) is left to T3 and remains to be finalized. The user has confirmed that issue production is “similar to filing a GitHub issue; details TBD”. There are three candidate approaches: (a) UserAgent directly produces IssueDraft in-character; (b) a separate analyzer reads the complete transcript and then synthesizes it; (c) two steps—first mark friction points, then synthesize them. T3 will first implement a minimal stub of (a) (the LLM produces 0..n drafts at the end of the session), without locking in the approach; the decision will be finalized when a later dev-side spec integrates concrete requirements.
