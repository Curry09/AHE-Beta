# 0009 · Pluggable Seed Workspace Supply (SeedSource Seam)

<!-- This file is maintained by the spec tool: the frontmatter contains structured source data (including the tasks DAG), and the body provides a group-level rust-RFC nine-section overview. -->

## Summary

This group follows up on spec-0008/T1: at that time, `SeedScenario.workspace` was implemented through `WorkspaceSpec{fixture, setup}` + `materialize()`, and the supply path was a **single, hard-coded local copytree**. As task sources increase (NL2Repo-style starting from an empty repository, and future SWE-bench / Terminal-Bench, among others), the **supply side must be pluggable**; the **consumption port**—`SeedScenario.description` text plus a workspace directory used as cwd by `Sandbox`/`sim_user`—remains frozen and unchanged.

This group abstracts “workspace supply” into an `SeedSource` protocol registered by `kind`: it downgrades the existing `materialize` into the first `local-fixture` implementation (behaviorally equivalent and backward compatible), and adds a lightweight `empty` source (creates an empty directory and optionally writes a requirements document, covering the NL2Repo-style “requirements document only” starting point) to demonstrate **additivity**—adding a source means adding one module (automatically discovered and registered), with zero changes on the registration or consumption sides. `workspace.materialize()` is reduced to a thin shell that delegates to the registry, so the `sim_user` bridge and the `Sandbox` call site remain unchanged.

**Explicit non-goals** (recorded only as extension points for downstream specs and not implemented by this group): Oracle / objective scoring (part of a parallel evaluation system, decoupled from the user's subjective verification); and a containerized “runnable handle” runtime (`run(cmd)`/`cleanup`). Dependency supply (venv/pip) was also originally listed as a non-goal and planned for a downstream effort, but is now correctly brought into this group as **T3** (see below)—because if “supply a workspace” does not include “make it runnable with its declared dependencies,” NL2Repo-style tasks with dependencies (for example, funcy requiring pytest/whatever) cannot run at all in a stdlib-only Sandbox. Git@commit retrieval was also originally listed as a downstream non-goal, but is now delivered as **T4** in this group (`git` source: clone repo@commit into a snapshot workspace)—the starting point for real repository tasks (SWE-bench's `base_commit` unpatched state, funcy@a particular version, and so on) is precisely “a repository stopped at a particular commit”; the two local sources (local-fixture/empty) cannot provide that starting point. This group advances the supply side: establish the seam (T1) + add a verified second implementation (T2) + activate `setup` dependency supply (T3) + add the general-purpose `git` snapshot source (T4); heavyweight frameworks (containers / Oracle / concrete benchmark adapters) remain downstream and are not created prematurely.

The backbone of the data flow (the numbering is also the execution order: first establish the seam in T1, then add a second source in T2 to prove pluggability, then activate `setup` dependency supply in T3 so the workspace can run its declared dependencies, and finally add the general-purpose `git` snapshot source in T4 to support real repository tasks):

```
seed scenario  SeedScenario.workspace = WorkspaceSpec{kind, fixture?, params, setup}
   │  Look up kind in the SeedSource registry (T1 establishes the protocol + registry + sources/ autodiscovery)
   ▼
SeedSource.provision(spec, dest) -> workspace_dir
   ├─ kind="local-fixture": copytree in-repo fixture       (T1, same behavior as 0008)
   ├─ kind="empty":         create an empty directory, optionally write a requirements document (T2, demonstrates extensibility)
   └─ kind="git":           clone repo + checkout <commit> (T4, real repo snapshot)
   ▼
Dependency provisioning: ensure_deps(dir, spec) executes spec.setup (may prepare a per-workspace .venv) (T3)
   ▼
Consumer interface unchanged: workspace.materialize() delegates through a thin wrapper → sim_user bridge → Sandbox(workspace=dir) uses it as cwd; by default, only cwd + ambient env are shared; the venv is used only with an explicit `.venv/bin/python ...`
```

## Motivation

0008/T1 enables seed scenarios to carry a workspace, but the supply path is hard-coded to the local copytree in `materialize`: when diverse task sources are added later (NL2Repo-style empty-repository starting points, SWE-bench / Terminal-Bench, and so on), changing `materialize` for every new kind would turn the supply side into an if/else patchwork. The motivation for this group is to extract “the mechanism used to prepare the workspace” into a pluggable seam (T1), while keeping the consumption port (`SeedScenario.description` + the workspace directory used as cwd by `Sandbox`) frozen; then use a second source requiring no new infrastructure, `empty` (T2), to verify that the seam is genuinely decoupled—`empty` directly expresses the minimal task shape of “an empty workspace + a natural-language request,” the injection shape for NL2Repo-style construction from scratch, locking down pluggability with “add one source = add one file, zero core changes” rather than merely declaring it.

Once the seam is established, it exposes two gaps that had previously been deferred as non-goals but cannot be avoided in practice. First, 0008/T1 and 0009/T1 both listed “dependency supply” as a non-goal, while `WorkspaceSpec.setup` left only a placeholder and did not execute it. As a result, `Sandbox` can currently run only against the host's ambient stdlib environment—tasks with third-party dependencies (most real repositories and some NL2Repo tasks) cannot actually run their declared verification. Take funcy as an example: the library itself uses only the stdlib, but its `start.md` declares that verification requires `pytest 7.4.3` + third-party `whatever 0.7`, and also requires `pip install -e .`; without dependency supply, the user agent cannot run `import whatever` in the Sandbox and therefore cannot run `ModuleNotFoundError` or `python setup.py test`. T3 fills this gap, making “supply a workspace” truly mean “supply a workspace that can run according to its declared dependencies,” closing the supply-side scope of this group.

Second, the two sources already implemented can only start locally: `local-fixture` copytrees an in-repository vendored directory, while `empty` creates an empty directory (and can optionally write a requirements document). The injection shape for real software engineering tasks is neither of these—it is “a working-tree snapshot of a particular public repository at a particular historical commit”: a SWE-bench instance is the unpatched state of `repo` at `base_commit`, and a funcy-style task is the source tree of a particular release. Without a “git clone @commit” source, the starting point for this class of tasks cannot be created at all, making the pluggable seam effectively irrelevant to real repository distributions. T4 fulfills this reserved extension point by adding the general-purpose `git` source, allowing the supply side to support task families “based on a particular repository snapshot” (the adapter layer from concrete benchmark fields to scenarios is a non-goal, as described below).

## Guide-level explanation

This group abstracts workspace supply from the “single hard-coded local copytree” into an `SeedSource` protocol registered by `kind` (T1): it defines `SeedSource.provision(spec, dest) -> workspace_dir` and an `kind → SeedSource` registry. At import time, the registry traverses the `sources/` package and automatically discovers each source, so adding a source requires no changes on the registration side. It migrates the `materialize` logic from 0008/T1 into the first `local-fixture` implementation; `WorkspaceSpec` adds `kind` (defaulting to `local-fixture`) and the general-purpose `params`; and `workspace.materialize()` becomes a thin shell delegating to the registry. This is the foundation of the group, and the numbering is the execution order: T1 establishes the seam first, after which the other three sources can be integrated purely by adding modules.

Two purely local sources are connected to this seam to verify additivity, followed by a remote source covering real repositories. T2's `empty` creates an isolated empty workspace directory; when `params` contains `doc`, it writes its text to a requirements document, covering the NL2Repo-style scenario of “only one requirements document, starting from an empty repository.” T4's `git` clones `repo` into an isolated workspace directory and `git checkout <commit>`, producing a clean snapshot of “a particular repository stopped at a particular commit” and fulfilling the extension point reserved by 0009 for “future SWE-bench / Terminal-Bench”—the starting point for real repository tasks (SWE-bench's `base_commit` unpatched state, funcy@a particular version, and so on) is precisely this snapshot, which the two existing sources cannot provide (`local-fixture` only copies a vendored directory, while `empty` only provides an empty directory). Both share the same constraint: integration requires **adding only one `sources/*.py` module** (`empty.py` / `git.py`); automatic package discovery and registration from T1 handles the rest, with zero changes to `seed_source.py` / `models.py` / `workspace.py` or the consumption side (sim_user / Sandbox). All parameters, including `doc`/`repo`/`commit`/`ref`/`depth`, are placed in the existing `WorkspaceSpec.params` and do not expand the schema. The `git` source is fresh for each session (a copy is cloned/checked out again for each round, isolated to prevent cross-session state, just like local-fixture is copied again for each session).

The final supply-side link is added by T3: it makes `WorkspaceSpec.setup` (only a placeholder since 0008 and never executed) real—after a source provisions a workspace directory, it prepares the dependency environment in that directory according to the `setup` command (which may be defined as a per-workspace `.venv` + pip installation). The workspace thereby advances from “has files” to “the declared setup has been executed.” Add `deps.py` (the setup executor) and invoke it at the shared workspace handoff point (the orchestrator, after materialize and before launch). The consumption side does not implicitly activate any venv; if the harness or user wants to use setup artifacts, it should do so naturally through an explicit command (such as `.venv/bin/python -m pytest ...`). Do not change any T1/T2/T4 files or expand the `WorkspaceSpec` schema (reuse the existing `setup`).

## Reference-level explanation

### The seam and three provision implementations

The core of the supply side is a dispatch chain:

```
WorkspaceSpec{kind, fixture?, params, setup}
        │ kind
        ▼
SeedSource registry  dict[str, SeedSource]   ◄── scan the sources/ subpackage at import time; each source registers itself
        │ provision(spec, dest_root) -> workspace_dir
        ▼
LocalFixtureSource(kind="local-fixture"): copytree seed_workspaces/<fixture>/project (T1, same behavior as 0008)
EmptySource(kind="empty"): create an empty directory, optionally write a requirements document (T2)
GitSource(kind="git"): clone repo + checkout <commit> (T4)
```

`SeedSource` (T1) is `Protocol`, specifying `kind: str` and `provision(spec: WorkspaceSpec, dest_root: str | None) -> str` (returning the absolute path of an isolated workspace directory). Registration works as follows: the `@register("<kind>")` decorator writes implementations into the module-level `_REGISTRY`; during import, `seed_source.py` uses `pkgutil.iter_modules` to traverse the `sources/` package and import each module, triggering registration by each source—this is the foundation of the “add a source = add one module” additive mechanism, on which both T2 and T4 depend without changing the registration side. The top-level `provision(spec, dest_root)` dispatches by looking up `spec.kind`; if no match is found, it raises `ValueError`, whose message lists the registered kinds.

Backward compatibility (T1): `WorkspaceSpec` adds `kind: str = "local-fixture"` and `params: dict = {}`; `from_dict` defaults a missing `kind` to `local-fixture` and a missing `params` to `{}`, so 0008 persisted data and `billing-split` fixtures remain usable as-is. `workspace.materialize(spec, dest_root)` is changed into an `return provision(spec, dest_root)` thin shell and retained as a compatibility shell rather than deprecated—the `sim_user` bridge and the `Sandbox` call site remain unchanged (the consumption port is frozen). `local_fixture.py` houses the original copytree logic (error when the fixture is missing, isolated copy for each session), migrated out of `workspace.py`; `workspace.py` retains only the compatibility shell and shared helpers such as `seed_workspaces_root()`.

The second and third sources verify “add a source = add one module” on this seam:

- T2 `empty` (`sources/empty.py`): defines `EmptySource`, and `@register("empty")` self-registers. It does not read `fixture`, and recognizes only `params`. `provision` creates an isolated directory (tempfile.mkdtemp or dest_root/<name>); when `params.doc` is non-empty, it writes its text to `params.doc_name` (defaulting to `SPEC.md`), and otherwise creates a purely empty directory, giving the inner agent a foothold for “reading the requirements document.” This covers the NL2Repo-style scenario of “only one requirements document, starting from an empty repository.”
- T4 `git` (`sources/git.py`): defines `GitSource`, and `@register("git")` self-registers. It reads `repo` (required, a URL or owner/repo) from `spec.params`, along with `commit` (required, the snapshot sha/ref to restore), optional `ref` (the branch/tag to target during cloning), and `depth` (shallow clone depth). In the isolated directory `git clone`, it performs an optional `--depth`/specified `ref` clone plus `git checkout <commit>` to restore the snapshot, then returns the absolute path of that directory. `repo` at `base_commit` is the SWE-bench unpatched state. It is fresh for each session: each round clones/checks out a new clean snapshot, using an independent directory that can be cleaned up, isolating sessions and preventing harness modifications or user-agent writes from the previous session from carrying over to the next, just as local-fixture is copied again for each session. It is orthogonal to T3 dependency supply: `git` is responsible only for “materializing a particular repository snapshot as a workspace”; environment setup (venv/pip, `pip install -e .`) is still prepared by T3 in that snapshot directory.

The two sources and local-fixture share the same isolation/return contract: every provision creates a completely new directory, does not contaminate other provisions, and returns an absolute path, so `Sandbox(workspace=dir)` can use it directly as cwd. Both sources add only one `sources/*.py` file (+ tests); the files owned by T1 and those of the other two sources are disjoint. All parameters, including `doc`/`doc_name`/`repo`/`commit`/`ref`/`depth`, are placed in the existing `params: dict`; the `WorkspaceSpec` schema is not expanded (T1's models.py is untouched). This is the criterion that the ports-and-adapters boundary holds: each of the second and third adapters adds only one file.

### Dependency supply (T3)

The final link in the supply chain, with the consumption port still frozen (directory + local shell):

```
SeedSource.provision(spec) -> workspace_dir      (T1/T2/T4, writes files to disk)
        │  orchestrator: after materialize, before launch
        ▼
deps.ensure_deps(workspace_dir, spec)            (T3, executes spec.setup to prepare dependencies)
        │  Convention: setup creates <workspace_dir>/.venv and installs packages into it with pip
        ▼
Both sides start with the shared workspace_dir:
   ├─ harness subprocess (SANDBOX_WORK_DIR=workspace_dir, 0008/T1v2)
   └─ User agent Sandbox(workspace=workspace_dir) (0008/T2)
            └─ run_shell only changes cwd and inherits the ambient environment; the venv is used only with an explicit `.venv/bin/python ...`
```

The hook belongs in the orchestrator rather than provision: for the same reason that 0008/T1v2 moves materialize up into the orchestrator, the workspace must be shared by both the harness and the user agent. If dependency preparation is declared by the scenario, it must land in the directory identified by both sides *before* launch; the orchestrator is the only layer that simultaneously knows the materialize result and the launch timing. This also means T3 only touches the cross-group orchestrator/sandbox and does not modify the T1/T2/T4 provision/materialize files (files are disjoint within each group). Reuse the existing `setup: list[str]` instead of adding a structured deps field to `WorkspaceSpec`: 0008/T1 has already reserved this hook, so the MVP can activate it directly without expanding the schema (and without touching T1's models.py); the venv convention lives in the data (commands), not in the code. A per-workspace `.venv` can be created by setup, at the cost of installing it for every session (caching remains an open question); however, Sandbox no longer implicitly detects/activates `.venv`, to avoid mismatches between users' private tools and the harness shell's default environment. If the harness or user needs to use this venv, it must explicitly run `.venv/bin/python ...` or an equivalent activation command, making environment selection an observable behavior within the task. Degradation and compatibility: when `spec.setup` is empty (including all existing fixture/empty/git scenarios), `ensure_deps` is a no-op, no `.venv` is generated, and Sandbox uses ambient; existing behavior is unchanged.

### Interface

- `SeedSource` (protocol, `sim/seed_source.py`): attribute `kind: str`; method `provision(spec: WorkspaceSpec, dest_root: str | None = None) -> str`.
- Registry API (`seed_source.py`): `register(kind: str)` decorator; `get_source(kind) -> SeedSource`; `provision(spec, dest_root=None) -> str` top-level dispatch; `available_kinds() -> list[str]`. The `sources/` subpackage automatically discovers registrations at import time.
- `WorkspaceSpec` (`models.py`): add `kind: str = "local-fixture"` and `params: dict[str, Any] = field(default_factory=dict)`; retain `fixture: str` (used by local-fixture) and `setup`. `to_dict` omits default items to preserve the old serialized shape; when `from_dict` lacks `kind`, use `local-fixture`; when it lacks `params`, use `{}`.
- `LocalFixtureSource` (`sources/local_fixture.py`): `kind="local-fixture"`; `provision` = copytree `seed_workspaces/<spec.fixture>/project` into a new isolated directory and return its absolute path.
- `EmptySource` (`sources/empty.py`): `kind="empty"`; `provision(spec, dest_root=None) -> str` creates a new isolated directory; when `spec.params.get("doc")` is non-empty, write `spec.params.get("doc_name", "SPEC.md")`. It is added to the registry through `@register("empty")`; callers still use the top-level `provision(spec)` and do not depend directly on this class.

## Rationale and alternatives

The seam-level choice (T1) focuses on keeping the cost of adding a new source at zero. Choose “subpackage automatic discovery + decorator self-registration” rather than a “centralized import list”: this gives new sources zero registration-side changes (T2 and T4 each only need one file added to integrate), at the cost of one directory scan at import time plus registration dependencies on import side effects. This is covered by a test that verifies the kind can be found without a manual import. The alternative, a “centralized list,” would require changing a shared public file every time a source is added, violating the extensibility goal, and is therefore rejected. `WorkspaceSpec` uses flat `fixture` + generic `params: dict` rather than “one strongly typed subclass per kind”: this avoids changing `WorkspaceSpec` when adding a source and keeps the serialized shape stable. T2's `doc`/`doc_name` and T4's `repo`/`commit`/`ref`/`depth` all occupy this extension point, at the cost that each source must validate its own required fields internally (local-fixture requires `fixture` to be non-empty). Retain the `materialize` thin wrapper rather than changing the 0008 call site: this keeps the consumer side unchanged and enables gradual migration, at the cost of one additional layer of indirection (acceptable).

The second and third sources are selected to serve different verification goals. The second source uses `empty` instead of directly implementing a git/container source: this verifies that the seam is decoupled at minimal cost (no new infrastructure; still a local directory). The tradeoff is that the “heavyweight provisioning” path is not covered—this is intentional; heavyweight runtime handles remain outside this group's scope and are left to downstream specs. Generic `params.doc`/`doc_name` are used instead of introducing a dedicated schema for `empty`, keeping `WorkspaceSpec` from growing with each source. The tradeoff is that `params` is weakly typed and relies on internal source validation and tests for constraints. The third source uses generic `git` instead of directly implementing a SWE-bench-specific source: generic clone@commit can be reused across all task families “based on a particular snapshot of a particular repository,” isolating benchmark-specific field mappings in a separate adapter. The tradeoff is that this task does not deliver an end-to-end path that can directly consume the SWE-bench dataset (the adapter is deferred to later work). It likewise uses generic `params.repo`/`commit` instead of a dedicated strongly typed schema, following the same structure as empty. `git` performs a fresh clone for each session instead of using a cache/shared bare mirror: this provides deterministic, isolated, clean snapshots that can be cleaned up, at the cost of time + requiring network access to the git source—cross-session clone caching/local mirror reuse is deferred to later work. `git` only solves “materializing a particular snapshot of a particular repository as a workspace”; environment robustness still relies on T3's `setup` (venv+pip). Instances sensitive to versions/system dependencies or requiring official images are not guaranteed to run—these fall under the existing container/hermetic non-goals, and this task does not expand its scope to build a heavyweight runtime.

Dependency provisioning (T3) activates the existing `setup` instead of building a new provisioner framework: following Occam's razor, it connects the dependency path with minimal changes. The tradeoff is that setup consists of weakly typed shell commands and relies on scenario authors to write them correctly (no lockfile resolution). A fresh venv is installed for each session: the environment is deterministic, isolated, and cleanable, at the cost of time and network dependency (pip requires access to a package source)—cross-session caching/prewarming remains an open-question and is outside the MVP. The Sandbox on the user agent side does not automatically use the venv: the default execution environment remains ambient + the same cwd, consistent with the harness. If a task requires the venv, both the harness and the user must explicitly invoke `.venv/bin/python ...`, making environment selection observable behavior within the task rather than implicit behavior at a platform seam. Non-security/non-hermetic: the sandbox still provides minimal isolation through cwd+timeouts, and the venv only addresses “dependency visibility,” not “malicious code/network isolation”—the 0008/T2 threat model is retained, with strong isolation left to downstream work. The hook is placed at “every production seam that materializes a workspace” rather than only in the orchestrator: on the main path, the orchestrator calls ensure after materializing the shared workspace; the sim_user direct fallback (which bypasses the orchestrator but still materializes the workspace itself) likewise calls ensure_deps symmetrically after materialization—ensuring that no production path that “creates a workspace” silently lacks dependencies (revision: an early version documented not calling ensure_deps on the fallback path as an acceptable tradeoff; in practice, this is a production seam that can silently lack dependencies, so it was consolidated into symmetric calls). The tradeoff is that symmetry must be maintained at both call sites; only standalone tools/independent smoke scripts (which bypass these two production seams and materialize workspaces themselves) must manage `ensure_deps` themselves (acceptable, as this is on the tooling side).

## Prior art

This group as a whole extends 0008/T1 (`materialize` and `WorkspaceSpec` in `workspace.py`, and `SeedScenario` in `models.py`); on the consumer side, the `sim_user` bridge from 0008/T1 and `Sandbox(workspace=dir)` from 0008/T2 are reused unchanged and remain outside the files of every task in this group. T1 establishes the protocol, the `register`/`provision` registry, and the `sources/` autodiscovery mechanism, and adds `kind`/`params` to `WorkspaceSpec`; T2's `empty` (`sources/empty.py`) and T4's `git` (`sources/git.py`) both integrate with the registry using only this seam and these two fields (without modifying T1 files). T4 integrates orthogonally with this group's T3 dependency provisioning: `git` materializes the snapshot, and T3's `setup`/`ensure_deps` prepares dependencies within that snapshot; together, they fulfill the provisioning-side extension point originally reserved in the 0009 frontmatter for “future SWE-bench / Terminal-Bench.” T3 activates the `WorkspaceSpec.setup` hook reserved by 0008/T1 but never previously executed. It runs after shared-workspace materialization in 0008/T1v2 (in the orchestrator, before run_session) and is consumed by `Sandbox` in 0008/T2 (run_shell injects the venv), resolving one of T1's open-questions and the dependency provisioning gap recorded in the 0008/T1 tradeoffs—after NL2Repo tasks such as funcy are imported through T2's `empty` source, T3 must prepare their declared dependencies before verification can actually run. Objective evaluation of NL2Repo-style tasks (scoring by running upstream tests) is repeatedly designated a non-goal in T2, T3, and T4 and belongs to a downstream parallel evaluation system.

## Unresolved questions

Operational details of dependency provisioning (from T3): cross-session venv caching/prewarming has not yet been implemented—fresh installation for every session takes time and requires network access; should a venv be cached and reused by (deps fingerprint), or should image layers be prebuilt? Should stronger environment description/reproduction conventions be provided (for example, requiring the harness's final response to state whether it used ambient python or `.venv/bin/python`)? Dependency provisioning in offline/restricted environments (offline mirrors, vendored wheels) is not yet covered. The source of setup commands—whether automatically generated from requirements documents (such as the dependency list in funcy `start.md`) or handwritten by the scenario/adapter; the former requires a “document→setup” derivation step and is deferred to later work. The policy for dependency installation failures—failing the entire session or degrading to “limited verification without that dependency”—is still undecided.

Whether the consumer port needs upgrading (from T1): whether future heavyweight sources (containerized SWE-bench / Terminal-Bench) require upgrading the consumer port from a “workspace directory” to an “executable handle {cwd, run(cmd), cleanup}” so that the Provider and (future) objective evaluation can share the same runtime capabilities—this group retains the “directory + local shell” port unchanged; whether and when to upgrade is left for downstream evaluation, with the goal of minimizing port rework when heavyweight sources are integrated.

Remaining gaps in supporting real repo tasks (from T4): the adapter layer from specific benchmark (SWE-bench, etc.) fields to `SeedScenario`/`WorkspaceSpec` has not yet been implemented—mapping a dataset instance's `repo`/`base_commit`/environment declarations to `params` consumable by this source + T3's `setup`. This group only provides a generic git source; the adapter is deferred to later work/a separate spec. Container/hermetic and version-pinned environment robustness—for instances sensitive to system dependencies or requiring official images, clone@commit + venv alone does not guarantee execution; the existing non-goal of “leaving heavyweight runtimes to downstream work” remains in effect. Oracle/objective scoring (running upstream tests to determine whether a fix is correct) is a held-out red line and must never enter this framework's training. Whether harness subprocess bash uses the workspace venv belongs to the harness side/developer evolution and is explicitly excluded from this group's framework scope (as in T3's open-question). Private repository authentication (injecting a token / ssh key into clone): this group defaults to public/local repositories; authentication is deferred to later work. Cross-session clone caching/local bare mirror reuse to save time and network access: this round performs a fresh clone for each session, with caching deferred to later work.
